# Qiita Trend Guard

Qiita のトレンド面から、組織的な「いいね」で押し上げられた記事を検出・排除する Chrome 拡張機能。

>
> **改訂 3 (2026-08-18)** — OQ-8 / OQ-9 を実測。**Atom フィードの `<updated>` に数分のラグがあるため、スキャン起動を時刻ベースから `<updated>` 変化検知へ変更**。ミュートに確認ダイアログは存在せず、Snackbar が完了を通知することが判明したため、**完了検知を固定 sleep から Snackbar 監視へ変更**。CSS-in-JS のハッシュクラス名に依存しないセレクタ戦略を追加。

## Problem Statement

Qiita のトレンド面が、複数アカウントによる組織的な「いいね」（相互 LGTM / 組織票）で押し上げられた記事に占拠されている。読者は再利用性の高い技術情報に辿り着けず、Qiita 創業時の理念である「再利用性・汎用性の高い情報が集まる場」が損なわれている。対処手段は手動のミュート／ブロックしかないが、対象アカウントが増え続けるため運用が破綻する。

## Evidence

- **実観測（本 PRD 作成者）**: 特定の 2 著者の記事 4 本において、likers 一覧に同一の顔ぶれが十数アカウント揃う。いいねしているアカウントは記事 0 本・プロフィール空に偏る。
  - ⚠️ **具体的な URL は下部「Appendix: 一次証拠」に隔離。公開記事には転載しないこと。**
- **公的な議論の存在**: 2021 年時点で「Qiita のトレンドが機能しなくなっている？→『大学の講義での相互 LGTM』が原因として浮上」として公に議論されている（[Togetter](https://togetter.com/li/1647298)）。**本問題は個人の体感に留まらない。**
- **実測 (2026-08-18)**: ミュート 2 名（対象記事 2 本）＋ ブロック（対象記事 3 本）を実行したところ、トレンドは **30 件 → 25 件**。**次の更新を迎えても 30 件に戻らず、backfill は行われない。**
- **公式仕様の確認**: `https://qiita.com/popular-items/feed` のルート `<updated>` が `2026-08-18T17:00:00+09:00`。トレンドセットは **5:00 / 17:00 の 1 日 2 回しか更新されない**。

## Proposed Solution

Manifest V3 の Chrome 拡張機能（TypeScript + Vite）。**ユーザーが開いているトレンドページの DOM から 30 件を読み取り**（追加リクエスト 0）、Qiita API v2 で各記事の likers を収集する。**「N 人以上の同じアカウント群が、同一著者の M 本以上の記事に共通していいねしている」というクラスタ共起パターン**と、**投稿直後の一斉いいね（バースト）**を検出する。該当した著者と当該アカウント群を候補として一覧提示し、ユーザーの**一括承認**により (1) 表示中ページでの DOM 即時非表示、(2) Qiita 本体でのミュートを実行する。

単一アカウントの共起ではなく**アカウント群のクラスタ性**を判定単位にするのが本質。単一共起は熱心な読者・同僚・勉強会仲間と区別できず、善良な著者を巻き添えにするため。

**データ取得は公式 API と公式フィードのみを使い、スクレイピングを一切行わない**（Qiita 公式ヘルプがスクレイピングを禁止しているため。後述）。

## Key Hypothesis

We believe **アカウント群の共起クラスタ検出 ＋ 一括承認によるミュート実行** will **「組織票記事を手動で排除し続ける運用破綻」を解消** for **Qiita のトレンド面を日常的に開く読者**。

We'll know we're right when **提示された候補の適合率が 80% 以上を維持し、かつ 1 回のスキャンあたりの手動操作が 1 クリックに収まったとき**。

## What We're NOT Building

- **あらゆる HTML ページの自動取得（スクレイピング）** — Qiita 公式ヘルプが明確に禁止している。`/likers` ページやユーザーページの自動 fetch を含め、一切行わない。
- **ブロックの一括自動実行** — ブロックボタンが native `alert()` を起動し、content script から閉じられない。単発の手動操作としてのみ残す。
- **広告掲載・収益化** — Qiita ヘルプが「アプリ等に広告を設置して収益化されることに関しては Qiita利用規約 違反」と明記。
- **共有ブロックリストの配布** — 判定結果を他者に配布した時点で、誤検知が第三者の評判被害に直結する。ローカル完結を貫く。
- **組織票の告発・告知機能** — Qiita 運営への通報や SNS 拡散の支援はしない。名誉毀損リスクの回避に直結する。
- **書き手向け分析ツール用途** — 「自分の記事のいいねは本物か」を調べる用途は提供しない。監視ツール化を避け、読者のフィルタに役割を限定する。
- **Qiita Team 対応** — 社内 Qiita にトレンドも組織票も存在しない。かつ Like API は 2020 年 11 月に廃止済み。
- **Qiita 以外のサイト（Zenn / note 等）** — v1 では横展開しない。
- **「登録直後アカウント」判定** — API の User オブジェクトに `created_at` が存在せず、直接判定が原理的に不可能。`items_count` / `followers_count` / `description` の合成による近似のみ補強シグナルとして使う。

## Success Metrics

| Metric | Target | How Measured |
|--------|--------|--------------|
| **適合率（Precision）** | **80% 以上** | 拡張機能内のフィードバック UI で、提示された候補ごとに「妥当 / 誤り」を記録し、`妥当 / (妥当 + 誤り)` を算出 |

**意図的に計測しない指標**: トレンド浄化率、手間の削減量、主観評価。

理由 — 本プロダクトの最大リスクは**誤検知による正当な著者の巻き添え**であり、指標を適合率 1 本に絞ることで閾値調整の判断を一意にする。他の指標は判断を曖昧にする。

**この指標の成立条件**: 適合率を測る以上、**フィードバック UI は Must-have**。計測手段のない指標は成立しない。

## Users & Context

**Primary User**

- **Who**: Qiita のトレンド面を日常的に開く**読者**（投稿しない ROM 層を含む）
- **Current behavior**: トレンドを開き、目についた記事を読む。ノイズは目視で読み飛ばす。目に余るアカウントを手動でミュート／ブロックするが、対象が増え続けて追いつかない
- **Trigger**: トレンドを開いた瞬間／「またこの顔ぶれか」と気づいた瞬間
- **Success state**: トレンド一覧が、実際に読む価値のある記事だけで埋まっている

**Job to Be Done**

**トレンドを開いたとき**、組織票で押し上げられた記事を**自動で排除したい**。そうすれば、**再利用できる情報に最短で辿り着ける**。

**Non-Users**

- **書き手**（優先度として読者 >> 書き手）。「自分の記事が埋もれる」問題は本プロダクトの副次効果に留め、主目的にしない
- **Qiita Team ユーザー**
- **組織票を告発したい人**
- **Qiita 以外のサイトのユーザー**

**Vision**

Qiita のトレンドが「**組織票の強さ**」ではなく「**再利用性・汎用性の高さ**」で決まる状態に戻す。

| **Must** | **表示中ページの DOM 読み取りによるトレンド取得** | 改訂 6 で Atom フィードから変更。フィードとトレンドページは**別集合**（実測で一致率 70%）であり、フィードを見ていると**ユーザーが見ている 9 件を一度もスキャンできない**。content script が表示中の DOM を読めば**追加リクエスト 0** で、URL・著者ハンドル・投稿時刻（`<time datetime>`）が揃う |

| **Must** | 共起クラスタ検出エンジン（N 人 / M 本 / 日数） | プロダクトの中核。単一共起では誤検知が不可避 |
| **Must** | **バースト検出（投稿直後の一斉いいね）** | API 経路が唯一の取得手段になり `created_at` が常に手に入るため、使わない理由がない。改訂 1 の Should から昇格 |
| **Must** | パラメータ調整 UI（スライダー） | 閾値は実データでしか決まらない。ユーザー自身が調整できる必要がある |
| **Must** | 候補一覧 UI | 「一括承認」モデルの前提。Chrome Web Store ポリシーも代理操作前の確認を要求 |
| **Must** | 適合率フィードバック UI（妥当 / 誤り の記録） | 唯一の成功指標を計測する手段。これが無ければ指標が成立しない |
| **Must** | DOM 即時非表示 | Qiita 側の反映を待たずに効く。表示中ページのみを対象とし追加リクエストを発生させない |
| **Must** | **除外件数バッジ表示** | OQ-1 で backfill されないことが確定。なぜ 30 件が減ったかを説明しないと不具合に見える。改訂 1 の Should から昇格 |
| **Must** | 一括ミュート実行（div ポップアップの自動操作） | 核心の痛み「増え続けるアカウントを手動で潰す手間」への直接解 |
| **Should** | ブロックの**単発**手動実行 | ユーザー要望。ただし一括自動化は不可（OQ-3） |
| **Could** | 検出履歴の時系列可視化 | 記事化の際の図表素材になる |

| **Won't** | **ブロックの一括自動実行** | native `alert()` を content script から閉じられない。MAIN world 注入で `window.alert` を潰す手法は壊れやすく挙動が攻撃的 |
| **Won't** | **HTML ページのスクレイピング** | Qiita 公式ヘルプが明確に禁止 |
| **Won't** | 広告掲載・収益化 | Qiita 公式ヘルプが利用規約違反と明記 |
| **Won't** | 共有ブロックリスト配布 | 誤検知が第三者被害に直結 |
| **Won't** | 「登録直後」判定 | API に `created_at` が無く原理的に不可能 |
| **Won't** | Qiita Team / 他サイト対応 | スコープ外 |

### MVP Scope

**v1 = ローカル未パック拡張として自分で使い、適合率を追い込む段階。** Chrome Web Store 公開は後続フェーズ。

含むもの:

1. アクセストークン設定（**必須**）
2. 表示中ページの DOM からトレンド 30 件を読み取り（追加リクエスト 0）
3. API 経由の likers 収集（`created_at` 込み）
4. 共起クラスタ検出（デフォルト **N=5 人 / M=2 本 / 直近 3 日**）＋ バースト検出
5. 候補一覧 UI ＋ パラメータスライダー ＋ 適合率フィードバック
6. DOM 即時非表示 ＋ 除外件数バッジ
7. 一括ミュート実行

**「直近 3 日」の定義**: トレンドは 5:00 / 17:00 の 1 日 2 回更新のため、**トレンドセット 6 回分**と定義する。常時ポーリングは不要で、スキャンも 1 日 2 回で足りる。

## Technical Approach

**Feasibility**: **HIGH** — 必要な情報はすべて公式手段で取得できることが確認済み。原理的な障害はない。

### データ取得はすべて公式 API / 公式フィード経由（スクレイピング禁止への準拠）

Qiita 公式ヘルプ [Qiita API・スクレイピングについて](https://help.qiita.com/ja/articles/qiita-api) より:

> 「スクレイピングはサーバーの負荷上昇への懸念があるため、Qiitaへのスクレイピングは許可しておりません」
>
> 「Qiita APIでご用意している機能の範囲内でしたら、アプリ等を開発いただいて問題ございません」

この方針に完全準拠するため、取得手段を以下に限定する。

| 目的 | 手段 | 認証 | 判定根拠 |
|---|---|---|---|
| トレンド 30 件の列挙 | `https://qiita.com/popular-items/feed`（**Atom 1.0**） | 不要 | 公式が配信しているフィード。スクレイピングに当たらない |
| 著者の直近記事 | `GET /api/v2/users/:user_id/items` | 任意 | 公式 API |
| 記事の likers | `GET /api/v2/items/:item_id/likes` | **必須** | 公式 API。`created_at` あり |
| 記事の非表示 | **ユーザーが開いたページ**の DOM 操作 | — | **追加リクエストがゼロ**。サーバー負荷懸念に該当しない |
| ミュート実行 | **ユーザーが開いたページ**上でのボタン操作代行 | — | ユーザー自身の操作の代行。スロットリングすれば手動と同負荷 |

**明示的に排除するもの**: `/items/:id/likers` ページの自動 fetch、ユーザーページの自動 fetch、トレンドページの自動 fetch、その他あらゆる HTML ページの自動取得。

### Atom フィードの仕様（実測）

- 形式: **Atom 1.0**（`xmlns="http://www.w3.org/2005/Atom"`）
- エントリ数: **30 件**
- 認証: **不要**
- ページネーション: なし
- ルートの `<updated>`: `2026-08-18T17:00:00+09:00` → 5:00 / 17:00 更新の裏付け
- ⚠️ **`<updated>` の反映には数分のラグがある。**17:00 を数分過ぎた時点でも `T05:00:00` のままで、その後 `T17:00:00` に切り替わる（OQ-8 実測）

### スキャンの起動条件（改訂 6 で全面変更 — 表示中ページの DOM を読む）

**Atom フィードを廃止した。** 2026-08-20 の実測で、`https://qiita.com/popular-items/feed` と `https://qiita.com/trend` は**別集合**であることが判明したため。

| 観測 | 値 |
|---|---|
| 共通 | 21 件 |
| ページにしか無い | 9 件 |
| フィードにしか無い | 9 件 |
| **一致率** | **70%** |

フィードを見ている限り、**ユーザーが画面で見ている 9 件を一度もスキャンできない**。その著者は原理的に検出できず、Phase 7 の非表示にも盲点が残る。差が生じる理由は未解明（OQ-13）だが、廃止するので実害は無い。

**代わりに content script が表示中ページの DOM を読む。**

```
ユーザーが qiita.com/trend または qiita.com/ を開く
    ↓
content script が表示中の 30 件を読む（追加リクエスト 0）
    ↓  a[href*="/items/"] から handle と item_id
    ↓  <time datetime="..."> から投稿時刻
service worker へ TREND_ITEMS で送る
    ↓
インデックスに無い記事だけ likes API を叩く
    ↓
429 が返ったらそこで停止（Rate-Reset を記録）
    ↓
マージ → パージ → 検出 → 同じページで非表示（Phase 7）
```

**これはスクレイピングではない。** `fetch` で HTML を取りに行くのではなく、ユーザーのブラウザが既にダウンロードして表示しているものを読むだけで、**リクエストが 1 本も増えない**。CLAUDE.md の設計上の約束 1 が最初から許可している経路である（「表示中ページの DOM 読み取り（追加リクエストゼロ）は可」）。

参考: `robots.txt` は `/trend` と `/` をクローラに開放し、逆に `/api/*` を `Disallow` にしている。ただし robots.txt はクローラの作法を定める文書で、公式ヘルプの規定を上書きしない。**DOM 読み取りを選ぶ理由は、この解釈に依存しなくて済むことにもある。**

**定期実行は引き続き持たない（改訂 5 の判断を維持）。** 起動契機はページを開いたときだけになり、`onInstalled` / `onStartup` の自動スキャンは見に行く先を失うため廃止する。`alarms` 権限は不要のまま。

#### DOM から取れるもの（2026-08-20 実測）

| 項目 | 取得元 | 備考 |
|---|---|---|
| 記事 URL | `a[href*="/items/"]` | 絶対 URL。**UTM パラメータ無し**（フィードには付いていた） |
| 著者ハンドル | 同 URL のパス | `https://qiita.com/{handle}/items/{itemId}` |
| item_id | 同 URL のパス | |
| **投稿時刻** | **`<time datetime="...">`** | **`2026-08-17T17:44:41Z` の秒精度 ISO 8601（UTC）。バースト判定がそのまま生き残る** |

⚠️ **1 カードにつき `a[href*="/items/"]` が 2 本ある**（タイトル付きと無しで 30:30 = 60 本）。**href で重複排除すること。**

⚠️ **CSS-in-JS のハッシュクラス（`.style-*`）は使用禁止**（設計上の約束 2）。URL のパス構造と `<time datetime>` は HTML 標準および Qiita の実質的な公開 API であり、リニューアルに耐える。

#### 廃止した Atom フィード方式の記録（改訂 4 まで採用・改訂 6 で廃止）

実装済みだったものを捨てた記録として残す。**取得できる項目は十分だった。問題は「取得できる 30 件が、ユーザーの見ている 30 件と違った」ことである。**

| フィードから取れたもの | 要素 |
|---|---|
| 記事 URL | `<link rel="alternate" type="text/html" href="...">`（⚠️ UTM パラメータ付き） |
| 記事 ID | `<id>`（⚠️ 内部の数値 ID で API のパスには使えない。URL 側から取る必要があった） |
| 著者ハンドル | `<author><name>` |
| 投稿日時 | `<published>` |
| 更新日時 | `<updated>`（ルート側が変化検知のキーだった） |

**DOM 版はこれらをすべて代替でき**（URL のパス構造と `<time datetime>`）、加えて UTM の罠と `<id>` の取り違えという 2 つの落とし穴が最初から存在しない。

### レート制限の扱い（改訂 6 で全面変更）

実測値（2026-08-19、`Rate-Limit` ヘッダー）: **認証なし 60 req/h（IP 単位）／ 認証あり 1000 req/h**。

**予測的な予算管理を行わない。** 残量から「あと何件叩けるか」を計算して手前で止める方式は、余白の見積もりという別の不確実性を持ち込むうえ、打ち切り状態の伝播という複雑さを全レイヤーに広げる。**429 が返るまで走り、返ったらそこで止める。**

| 場面 | リクエスト数 |
|---|---|
| ページを開く（DOM 読み取り） | **0** — 表示中の DOM を読むだけ |
| 初回訪問（新着 30 件の likers） | 30 |
| **リロード**（全件インデックス済み） | **0** |
| トレンド更新後（差分のみ） | 9〜21 |
| フルモード: 著者の記事一覧＋過去記事 | ＋約 90 |

**中断しても壊れない。** インデックスは `itemId` で重複排除しながら蓄積するため、429 で止まった残りは次にページを開いたときに自然に拾われる。打ち切り専用の状態管理（`truncated` の伝播、保存の抑止）は不要になる。

**429 を受けたら `Rate-Reset`（epoch 秒）を記録し、バッジとポップアップで伝える。**「あと N 分で再開できます」と正確に出せる。あわせてフルモード（1000 req/h）を案内する。

⚠️ **429 は想定内の停止信号であり、`logger.warn` に載せてはならない。** Chrome は warn もエラー欄に集めるため、無料プランの正常な挙動が「拡張の不具合」として記録される（改訂 5 と同じ失敗の再来になる）。`logger.debug` に留め、ユーザーへは UI で伝える。

### likes の再取得（OQ-14 の決定）

**ライトモードは 1 記事につき 1 度だけ取得する。**`itemId` がインデックスにあれば skip し、リロードでは 0 req で済ませる。

**フルモードは一定時間後に再取得する。** 理由は敵対的な回避への備え: **この拡張の存在が知られた場合、いいねの時刻をずらされるとバースト判定が効かなくなる。**初回観測時のスナップショットしか持たないと、あとから揃えられた分を永久に見落とす。1000 req/h の余裕をここに使う。

これは**取得戦略の差であって判定ロジックの分岐ではない**。`detectCandidates` は依然としてインデックスを受け取るだけで、モードを引数に取らない。

### Architecture Notes

- **Manifest V3** / `host_permissions: ["https://qiita.com/*"]`
- **service worker**: API 呼び出し、スキャンのオーケストレーション、429 ハンドリング、スロットリング。**ネットワークから HTML は取得しない**
- **content script**: `https://qiita.com/` および `https://qiita.com/trend` に注入。**表示中ページの DOM を読んでトレンド 30 件を service worker へ渡し、判定結果を受けて非表示にする**（fetch は行わない）。ミュート実行時のみメニューと Snackbar を操作
- **DOM セレクタは 1 ファイルに集約**し、Qiita のリニューアルに対する被害を局所化する

### DOM セレクタ戦略（CSS-in-JS ハッシュへの依存を禁止）

Qiita の DOM で観測されたクラス名は `style-5ctx60` / `style-1pjbo7h` / `style-bv91a3` / `style-ajsqfw` / `style-o2lplv` といった形式で、**CSS-in-JS が生成したハッシュ**である。**Qiita がビルドし直すたびに変わるため、セレクタとして使用してはならない。**

| 優先 | セレクタ | 安定性の根拠 |
|---|---|---|
| 1 | `[id^="Snackbar-react-component-"]` | コンポーネント名は安定。uuid サフィックスのみ可変 |
| 2 | `[aria-live="polite"][aria-atomic="true"]` | ARIA 属性は事実上の契約であり、変更されにくい |
| 3 | `p` の `textContent` が「ミュートが完了しました」/「ミュートの解除が完了しました」 | 日本語コピー。変わりうるが変化を検知しやすい |
| 4 | `material-symbols-outlined` ＋ リガチャ `check_circle` | アイコンフォントの指定 |
| ❌ | `.style-*` すべて | **ビルドごとに変わる。使用禁止** |

観測された 2 種の Snackbar は uuid が同一だったため、**コンテナはページごとに 1 回マウントされ中身のみ差し替わる**構造と判断する。`MutationObserver` でコンテナを 1 回監視すれば足りる。

**完了検知**: 固定 sleep で待たず、Snackbar のテキスト出現を待って次の 1 件へ進む。「ミュートの解除が完了しました」は誤検知の巻き戻し経路で同じ仕組みを使う。

**ストレージ設計**（実測値に基づく）:

| 領域 | 上限 | 用途 |
|---|---|---|
| `chrome.storage.local` | **10 MB** | 共起インデックス、候補履歴、適合率ログ、アクセストークン |
| `chrome.storage.sync` | **100 KB / 8 KB per item / 512 items / 1800 writes per hour** | ユーザー設定（N・M・日数）のみ |

共起インデックスを `sync` に載せると即座に上限を超えるため **`local` 固定**。**アクセストークンも `sync` に置かず `local` に保存**する（同期による漏出面の拡大を避けるため）。

**データ構造**（合成値。日付は ISO 8601 / JST オフセット付き）:

```

  token: "<qiita_access_token>"              // 同期しない
```

### トークンの有無によるモード（改訂 4 で全面変更）

**改訂 3 までの「likers API は認証必須」は誤りだった。**2026-08-19 の実測で、認証なしでも HTTP 200 が返ることを確認した。トークンの有無がもたらす差は機能の可否ではなく **レート枠** である。

| | **ライトモード**（トークン未設定） | **フルモード**（トークン設定済み） |
|---|---|---|
| レート枠 | 60 req/h（IP 単位） | 1000 req/h |
| トレンド列挙 | 表示中ページの DOM（0 req） | 表示中ページの DOM（0 req） |
| likers 取得 | ✅ トレンド 30 件のみ | ✅ トレンド 30 件 ＋ 著者の過去記事 |
| 共起の判定範囲 | **トレンド 30 件の中での共起** | **同一著者の複数記事にまたがる共起** |
| バースト判定 | ✅ | ✅ |
| 空アカウント指標 | ✅（likes 応答に User が同梱される） | ✅ |
| 1 スキャンの消費 | 約 30 req | 約 120 req |

→ **設定ゼロで動く。**トークンは「使えるようにするもの」ではなく「**検出の射程を広げるもの**」。

→ ただし **OQ-12 が未解決**: ライトモードの射程（トレンド 30 件）で一次証拠のクラスタを実際に捕まえられるかは未検証。Phase 5 で確認する。

### API 制約（調査済みの事実）

- ✅ `GET /api/v2/items/:item_id/likes` — **認証不要**（2026-08-19 実測。改訂 3 までの「認証必須」は誤り）。Like オブジェクトに **`created_at` あり**
- ✅ **likes の応答に User オブジェクトが同梱される** — `items_count` / `followers_count` / `description` などが同じ 1 リクエストで手に入り、**空アカウント判定のための追加 API 呼び出しが不要**
- ✅ **`Total-Count` / `Link` ヘッダーあり** — 1 リクエスト目でページネーションの要否を判定できる（`rel="last"` にページ数が入る）
- ✅ **ミュートは likes API の結果に影響しない**（OQ-7、能動実験で確定）
- ✅ User オブジェクト: `items_count` / `followers_count` / `followees_count` / `description` / `organization` — 空アカウント判定の補強に使える
- ✅ `https://qiita.com/popular-items/feed` — Atom 1.0、30 件、認証不要
- ❌ User オブジェクトに **`created_at` なし** → 「登録直後」判定は不可能
- ❌ **「あるユーザーがいいねした記事一覧」のエンドポイントが存在しない** → 記事 → likers の方向にしか辿れず、**逆引きインデックスの構築が必須**
- ❌ **トレンド取得の API エンドポイントは存在しない** → **表示中ページの DOM 読み取りで代替**（改訂 6。Atom フィードは一致率 70% のため廃止）
- ❌ **ミュート / ブロックの API が存在しない** → 実行は表示中ページの DOM 操作のみ

### Technical Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| **誤検知で正当な著者をミュートする** | **H** | 判定単位をクラスタにする／一括承認を必須にする／ミュートのみ実行（`https://qiita.com/settings/mutes` から一括で戻せる）／適合率を常時トラッキング |
| **アクセストークン必須が導入障壁になる** | **H** | 設定手順を UI 内に埋め込む。Web Store 公開時の説明文で前置きする。トークン未設定時は「何ができないか」を明示 |
| **API がミュート対象を除外して返す**（OQ-7） | M | 未検証。除外される場合、ミュート実行後に検出履歴の継続性が失われるため、実行前のインデックスを保持する設計にしておく |
| **CSS-in-JS のハッシュクラス名に依存して即座に壊れる** | **H** | `.style-*` の使用を禁止。`[id^="Snackbar-react-component-"]` / ARIA 属性 / テキスト一致のみを使う（「DOM セレクタ戦略」参照） |
| DOM セレクタが Qiita のリニューアルで壊れる | M | セレクタを 1 ファイルに集約。取得失敗時は**何もしない**フェイルセーフ（誤った対象をミュートするより無害） |
| ミュートを起動するメニューの DOM が未取得 | M | OQ-9 の残件。Phase 8 の着手時までに実測する。Phase 2〜7 はブロックされない |
| 一括自動操作が Qiita 側に不正利用と見なされる | M | スロットリング（1 件あたり数秒間隔）、1 回の実行件数に上限。取得は API のみでスクレイピングは行わない |
| **スクレイピング禁止への抵触** | **L**（対策済み・改訂 6 でさらに後退） | ネットワークから取得するのは**公式 API のみ**。HTML は一切 `fetch` しない。DOM は**ユーザーが既に表示しているページ**の読み取りと操作代行だけで、**リクエストを 1 本も増やさない**。この構成なら規約やヘルプの解釈に依存しない |
| API レート制限超過 | **L**（改訂 6 で設計に組み込み） | 予測せず 429 まで走る。中断してもインデックスは `itemId` で重複排除しながら蓄積するため、残りは次にページを開けば拾える。ユーザーへはバッジで「あと N 分」とフルモードを案内 |
| **ページの DOM 構造が変わる** | **M**（新規・改訂 6） | 依存するのは URL のパス構造（`/{handle}/items/{itemId}`）と `<time datetime>` のみ。どちらも HTML 標準ないし Qiita の実質的な公開 API で、CSS-in-JS のハッシュクラスと違いリニューアルに耐える。取得失敗時は `null` を返して何もしない（設計上の約束 3） |
| **トレンドページが遅延描画される** | **M**（新規・改訂 6） | `run_at: document_idle` でも要素が揃っていない可能性がある。Phase 4b の着手時に実測し、必要なら MutationObserver でリトライする |
| Chrome Web Store 審査での却下 | **L** | 「代理操作にはユーザー確認が必要」というポリシー要件を、一括承認モデルが既に満たしている |
| ミュート件数の上限に達する（OQ-2） | **L** | 上限不明だがリスク受容。大量ミュート運用が常態化した段階で再検証 |

**Phase 1: 実測・仕様確定** — ✅ complete

**Phase 2: 基盤構築**

- **Goal**: 以降のフェーズが乗る土台を用意する
- **Scope**: Vite + TypeScript の MV3 ビルド構成、`manifest.json`、content script / service worker の骨格、**DOM セレクタを 1 ファイルに集約する構造**
- **Success signal**: 未パック拡張として読み込め、トレンドページで content script が動作する

**Phase 3: トークン設定 UI**

- **Goal**: フルモードへの移行手段を用意する（**検出の前提条件ではない**）
- **Scope**: アクセストークンの入力フォーム、`GET /api/v2/authenticated_user` による疎通検証、`chrome.storage.local` への保存、トークン取得手順の案内文、**現在のモード表示**
- **Success signal**: トークンを入力すると疎通確認が通りフルモードに切り替わる。未設定時は「ライトモードで動作中。設定すると検出の射程が広がる」ことが UI に明示される
- **実測済み（2026-08-19）**: `GET /api/v2/authenticated_user` は有効なトークンで HTTP 200 と 18 キーの User を返し、`Rate-Limit` が 1000 になる。**このエンドポイント 1 本で疎通検証とモード判定の両方が賄える**

**Phase 4b: データ取得層（DOM 版）** — 改訂 6 で新設

- **Goal**: **ユーザーが実際に見ている 30 件**を検出の入力にする
- **なぜ作り直すか**: Atom フィードとトレンドページの一致率が **70%** しかなく、フィードを見ている限りユーザーが見ている 9 件を永久にスキャンできない（上の「スキャンの起動条件」節を参照）
- **Scope**:
  - `src/dom/selectors.ts` にトレンドカードの読み取りを追加（`a[href*="/items/"]` の href 重複排除 ＋ `<time datetime>`）
  - `src/content/content-script.ts` が読み取り結果を `TREND_ITEMS` メッセージで service worker へ送る
  - `scanner.runScan(items)` — フィードを取りに行かず、引数で受け取る形へ
  - 429 で停止し `Rate-Reset` を記録。バッジとポップアップで「あと N 分」とフルモードを案内
  - フルモードのみ、一定時間後に likes を再取得（OQ-14）
- **廃止するもの**: `src/feed/atom-parser.ts`、`src/feed/feed-fetcher.ts`（＋各テスト）、`FeedSnapshot` 型、`LocalState.feedETag` / `lastFeedUpdated`、`storage.getFeedCache()` / `saveFeedCache()`、`rate-budget.ts` の予算計算（`availableRequests` / `RATE_SAFETY_MARGIN` / `fallbackLimitFor`）、`ScanProgress.budget`、`truncated` の伝播、`service-worker.ts` の `onInstalled` / `onStartup` 自動スキャン
- **Success signal**: トレンドページを開くと、**画面に出ている 30 件ぶん**の likers が `created_at` 付きで `chrome.storage.local` に入る。リロードでは API を 1 度も叩かない
- **検出エンジン（Phase 5）は無傷**: `src/detect/` はインデックスを受け取るだけで出所を問わない設計にしてあるため、この作り直しの影響を受けない
- **実装状況（2026-08-20）**: 上記 Scope のうち **OQ-14（フルモードでの likes 再取得）と 429 のバッジ／ポップアップ表示を除いて完了**。429 は `storage.rateLimitedUntil`（Unix 秒）に記録するところまでで、表示は Phase 6
- **実機確認済み（2026-08-20）**: 初回スキャンで `trend items: 25 new: 25` → `accounts: 308 records: 363` → **候補 2 件**。リロードで `new: 0` かつ API 呼び出しゼロ。`rate-remaining: 35` は 60 − 25 で、**1 記事 = 1 リクエストが実測で確認できた**
- **最大リスクは空振りした**: `run_at: document_idle` の時点でトレンドカードは揃っており、**遅延描画は起きなかった**。MutationObserver は入れていない。先回りして入れていたら、必要だったかどうかが永久に分からなくなっていた
- **25 件は 30 件の取りこぼしではない**: 2026-08-18 の実測（ミュート 2 名 ＋ ブロック 1 名 = 対象記事 5 本で 30 → 25）と完全に一致する。**DOM を読む設計では、ユーザーに見えている件数が正しい入力である**（OQ-6 の結論が反転、OQ-16 を新設）

**Phase 4（旧・Atom フィード版）** — superseded

- **Goal**: スクレイピングを一切行わずに検出の入力を揃える
- **Scope**: Atom フィードの conditional GET と XML パース、**`<updated>` 変化検知によるスキャン起動**（インストール時／ブラウザ起動時／手動。定期実行なし）、`GET /api/v2/users/:user_id/items`、`GET /api/v2/items/:item_id/likes`、レート制限ハンドリング、スロットリング
- **Success signal**: 1 回のスキャンで、トレンド 30 件分の likers が `created_at` 付きで `chrome.storage.local` に入る。かつ `<updated>` が変わらない限りスキャンが走らない
- **モード対応**: レート枠（60 / 1000 req/h）に応じて取得範囲を切り替える。`Rate-Remaining` ヘッダーを追跡し、枠を使い切る前に打ち切る。ページネーションの要否は `Total-Count` で判定する
- **OQ-7 は解決済み**（2026-08-19 実測）。ミュートは likes API の結果に影響しないため、実行前インデックスの保持は**不要**
- **User の追加取得は不要**。likes の応答に User が同梱されるため、空アカウント指標のための `GET /api/v2/users/:user_id` は呼ばない

**Phase 5: 検出エンジン**

- **Goal**: 組織票クラスタを判定できる
- **Scope**: アカウント → 記事の逆引きインデックス構築、共起クラスタ判定（N / M / 日数）、バースト判定（`Like.created_at` と記事の投稿時刻の差）、空アカウント指標による補強スコア
- **2 モード対応**: ライトモードは**トレンド 30 件の中での共起**、フルモードは**同一著者の複数記事にまたがる共起**。判定の骨格（N 人が M 本に共通）は同一とし、入力する記事集合だけを変える。**判定ロジックを 2 本持たない**
- **Success signal**: Evidence に挙げた 4 記事の実データで、当該クラスタが検出される
- **OQ-12 の検証**: **ライトモードの射程でも検出できるか**を同時に確認する。4 記事は 2 著者に属するため、トレンド 30 件の範囲内で共起が成立するかは自明ではない

**Phase 5b: 検出の穴を塞ぐ**（2026-08-23 の実機調査で新設）

- **Goal**: 実在する手口を取りこぼさない
- **背景**: ユーザーが目視で見つけた 2 著者（同一組織・いいねした顔ぶれが共通）を、**ライトでもフルでも 1 件も検出できなかった**。原因は 3 つあり、性質が異なる
- **Scope**:
  1. **著者巡回の起動条件**（バグ）: 著者を `newItems` からしか取らないため、トレンド記事が全件既知だと著者巡回が 1 度も走らない。**ライトモードで蓄積したあとにトークンを設定した場合、その著者の過去記事は永久に取りに行かない。**「リロードで無駄に 30 req 使う」問題への修正が反対側に振り切れた形。著者ごとの訪問記録を持つ（OQ-14 の再訪間隔と同じ器）
  2. **判定窓と取得射程の整合**（OQ-17）: `withinLookback` が `itemPostedAt` で切るため、フルモードで取った過去記事が判定に入らない。**共起の証拠は保持期間（7 日）すべてを使い、「新しさ」の制約は候補にする著者の選定へ移す**
  3. **著者をまたぐ共起**（OQ-18）: 記事 1 本の著者を捕まえる唯一の道。「別々の著者の記事に、同じ N 人が揃う」を判定軸として追加する。既存の著者内クラスタは残す（**ライト／フルで判定を分けないという約束 9 とは別の話**。手口ごとに判定軸を持つことは許される）
- **Success signal**: 調査で使った 2 著者の**両方**が候補に出る。かつ 351 記事ペアのうち候補になるのは異常値の 1 組だけ（誤検知が増えない）
- **2 段階に分ける（2026-08-23 決定）**: **5b-1 はバグ 2 件のみ**（上記 1・2）。3 は 5b-2 へ。バグを直すとフルモードが初めて正常に動き、数日ぶんの実データが貯まる。**閾値の根拠が実測 1 スキャン（351 ペア中 1 組）しかない状態で判定を作ると、その 1 件に合わせた判定になる**
- **判定は 1 本のまま（2026-08-23 決定）**: 約束 9 を維持する。「フルモードを主軸にしたい」は**既定値**で実現する — `lookbackDays` の既定を 3 → 7 にし、ライトは「トークンなしでも一応動く縮退版」と位置づける。`detectCandidates` は引き続き `ScanMode` を知らない
- **未確定（5b-2）**: 著者間クラスタが成立したとき `Candidate` に「同じクラスタの他の著者」を持たせるか。根拠として UI に出す必要がある。**optional な `coAuthors?` で足す想定**（既存コードへの波及を最小にするため）

**Phase 6: 候補 UI・設定 UI**

- **Goal**: ユーザーが確認して一括承認できる
- **Scope**: 候補一覧（著者 + 共起アカウント群 + 根拠の提示）、N / M / 日数のスライダー、「妥当 / 誤り」フィードバックボタン、適合率の表示
- **Success signal**: 候補を目視レビューし、適合率が算出・表示される

**Phase 7: DOM 非表示**

- **Goal**: Qiita 側の反映を待たずに効かせる
- **Scope**: 表示中ページでの候補記事の非表示、**除外件数バッジ**、セレクタ取得失敗時のフェイルセーフ
- **Success signal**: トレンドから対象記事が消え、「N 件を非表示にしました」が表示される
- **制約**: fetch は一切行わない。既に描画されている DOM のみを対象とする

**Phase 8: 一括ミュート実行**

- **Goal**: 核心の痛み「手間」を解消する
- **Scope**: 承認された候補に対するミュートメニューの自動操作、**Snackbar のテキスト出現による 1 件ごとの完了検知**（固定 sleep を使わない）、スロットリング、失敗時の記録とリトライ
- **Success signal**: 候補一覧から 1 クリックで複数件のミュートが完了し、`https://qiita.com/settings/mutes` に反映されている
- **前提**: OQ-9 の残件（ミュートを起動するメニューの DOM）を着手前に実測する。完了検知側の構造は取得済み
- **確認ダイアログは存在しない**: ミュートはクリックで即実行され、Snackbar が結果を通知するのみ
- **スコープ外**: ブロックの一括実行（native `alert()` により自動化不可）

**Phase 9: 適合率計測・閾値調整**

- **Goal**: 成功指標を達成する
- **Scope**: 実運用でのフィードバック蓄積、N / M / 日数のデフォルト値見直し、バーストスコアと空アカウント指標の重み調整
- **Success signal**: **適合率 80% 以上**

**Phase 10: 記事化**

- **Goal**: 一連のプロセスを Qiita 記事として公開する
- **Scope**: 拡張機能の紹介と、Claude Code で PRD → 実装まで走らせた開発プロセスの両方を扱う
- **制約**: **実アカウント名・具体的な記事 URL は一切掲載しない**（名誉毀損リスクの回避）。統計値と手法の説明に留める
- **素材**: 「スクレイピング前提で設計 → 公式ヘルプの禁止規定を発見 → Atom フィード＋API で再設計」という転回は、記事の核になりうる
- **Success signal**: 記事が投稿され、実アカウントを特定できる情報が含まれていない

### Parallelism Notes

- **Phase 3 と 4 は並行可能**。トークン UI は保存先を決めるだけ、データ取得層は API クライアントの実装で、互いの完成を待たない（結合は Phase 5）
- **Phase 6 と 7 は並行可能**。どちらも Phase 5 の検出結果を入力にするだけで、互いに独立している
- **Phase 8 は 6 を待つ**。承認 UI がなければ実行の起点がない
- **Phase 9 と 10 は直列**。適合率が固まる前に記事を書くと、結論のない記事になる

## Research Summary

### Market Context

- **Qiita 公式のミュート/ブロックは存在する。** ミュートはホーム / タイムライン / **トレンド** / 質問フィード / ストックリスト / タグ / 検索 / キャンペーンページに効く。ブロックはミュートの効果に加え、フォロー解除・再フォロー拒否・コメント拒否等が可能。**ブロックしたことは相手に通知されない。**
- **ミュートは `https://qiita.com/settings/mutes` で一覧確認・解除ができる。ブロックには対応する一覧 URL が存在しない**（解除は対象ユーザーのページ等から個別に行う必要がある）
- **先行する Chrome 拡張は 3 つ確認。すべて手動登録方式で、自動検出は皆無。**
  - Qii-U-Blocker（ユーザーページのボタンで手動追加 → ホーム / タイムライン / トレンドで非表示）
  - nGiita（手動ブロックリスト → Qiita 全ページで非表示）
  - Zenn・Qiita ミュート拡張（手動ミュート）
- → **「自動検出」は明確な空白地帯**であり、唯一の差別化ポイント。同時に「増え続けるアカウントを手動で潰す手間」という核心の痛みに直撃する。
- 組織票問題は 2021 年時点で公に議論されており、Evidence は個人の体感を超えている。

### Technical Context

- **Qiita はスクレイピングを許可していない**（公式ヘルプに明記）。一方で **API 利用は明示的に許可**されており、**広告による収益化のみ利用規約違反**とされている
- `https://qiita.com/popular-items/feed` は **Atom 1.0 / 30 件 / 認証不要**。`<author><name>`・記事 URL・`<published>` が取得でき、ルートの `<updated>` が `17:00:00+09:00` で更新スケジュールを裏付ける
- Qiita API v2 のレート制限: **認証時 1000 req/時、未認証 60 req/時（IP 単位）**。ページネーションは `page` 1–100、`per_page` 1–100
- `GET /api/v2/items/:item_id/likes` は**認証不要**（2026-08-19 実測）で **`created_at` と User オブジェクトを返す** → バースト検出と空アカウント判定が 1 リクエストで賄える
- **「ユーザーがいいねした記事一覧」「トレンド」「ブロック / ミュート」の API エンドポイントはいずれも存在しない**
- ミュート / ブロック後も **likers ページは閲覧可能**（API 側の挙動は未確認 = OQ-7）
- **ミュートには確認ダイアログが存在しない。**クリックで即実行され、`aria-live="polite"` の Snackbar が「ミュートが完了しました」/「ミュートの解除が完了しました」を通知する。**ブロックボタンは native `alert()`** を起動し、content script から閉じられない。ユーザーページ・トレンドページとも同挙動
- **Qiita の DOM のクラス名は CSS-in-JS 生成のハッシュ**（`style-5ctx60` 等）で、ビルドごとに変わる。安定するのは `[id^="Snackbar-react-component-"]` のような id プレフィックス、ARIA 属性、テキスト内容のみ
- **Atom フィードの `<updated>` には数分の反映ラグがある。**17:00 を過ぎても `T05:00:00` のままの期間が存在するため、時刻ベースのスケジューリングは成立しない
- 非ログイン時の `https://qiita.com/` がトレンドとして機能し **30 件**。ログイン時の `https://qiita.com/trend` が 25〜27 件なのは**ミュート適用後の残り**であり、構造的な差ではない
- **トレンドの更新は 5:00 / 17:00 の 1 日 2 回**、かつ **backfill されない**
- `chrome.storage.local` = 10 MB、`chrome.storage.sync` = 100 KB / 8 KB per item / 512 items / 1800 writes per hour
- Chrome Web Store ポリシーは、ユーザーの代わりに行う操作について**内容と対象をユーザーが確認できること**を要求。権限を伴う操作をバックグラウンドで黙って実行することを認めない
- Qiita 利用規約本体にスクレイピング・API 利用・ランキング操作を直接禁じる条文は無いが、**第 11 条 5 項 1 号「他人の個人情報を盗用、収集、蓄積、変更、利用する行為」**が本機能の中核と接する。ローカル完結・外部送信なし・保持期間 7 日・共有配布なしで距離を取る
