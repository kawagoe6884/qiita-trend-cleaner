## Deviations from Plan

### 1. `recompute(settings, now, persist)` を 2 つの関数に分けた

- **WHAT**: 計画は 1 関数 ＋ boolean 引数。実装は `previewCandidates`（計算のみ）と `applySettings`（計算＋保存）
- **WHY**: boolean 引数は呼び出し側で意味が読めない（`recompute(s, now, true)` の `true` が何かは定義を見ないと分からない）。保存するかどうかは**呼び分けたい 2 つの動作**であって、パラメータではない

### 2. `getSettings` を項目ごとのフォールバックにした

- **WHAT**: 計画は「3 つの数値が揃っていなければ `DEFAULT_SETTINGS`」。実装は項目ごとに既定値へ倒す
- **WHY**: 全体で倒すと、あとで 4 つ目の項目を足したときに、旧スキーマで保存済みのユーザー設定 3 つが巻き添えで消える

### 3. `recordVerdict` を `popup-state.ts` に足した

- **WHAT**: 計画には無かった。`popup-page.ts` から `storage.saveVerdict` を直接呼ぶ想定だった
- **WHY**: DOM 配線層に storage の import を持ち込むと、層の分離が崩れる。判定の保存と適合率の再計算はセットなので、1 つの関数として state 層に置いた

### 4. `logger.error` を 6 件増やした（**受け入れ基準に反する**）

- **WHAT**: 計画の Acceptance Criteria に「`logger.warn` / `logger.error` を新たに増やしていない」と書いたが、`popup-page.ts` に 5 件、`main.ts` に 1 件増えた
- **WHY**: **基準の書き方が絶対的すぎた。** 実際の規約（CLAUDE.md の約束 11）は「**想定内の失敗**を warn / error に載せない」であり、増やすこと自体の禁止ではない。追加した 6 件はすべて storage の読み書き失敗や `openOptionsPage` の失敗で、通常運転では 1 度も起きない。`options-page.ts` が同じ場所に同じ数の `logger.error` を持っており、その前例に揃えた
- **判断**: 下げない。**下げると本当に壊れたときに気づけなくなる。**ただし基準の文言が誤っていたことは記録する

### 5. `persistIndexAndDetect` が候補件数を返すようにした

- **WHAT**: 戻り値 `void` → `number`
- **WHY**: バッジに件数を出すのに、`persistScan` 側から候補数が見える必要があった。再度 storage を読むのは無駄

## Issues Encountered

### 1. tsc が型から消えたフィールドを検出しなかった

`Candidate` から `verdict` を削除したあと、`tsc --noEmit` が報告したのは `storage.test.ts` の **1 件だけ**だった。`detector.ts:35` の `verdict: null` は素通りしている。

```ts
findClusters(scoped, settings).map<Candidate>((hit) => ({
  ...
  verdict: null,   // ← 型に存在しないのにエラーにならない
}));
```

`.map<Candidate>()` の型引数経由では object literal の freshness チェック（余剰プロパティ検査）が効かない。**型から消したフィールドを、実行時には書き続けていた。**`grep verdict` で見つけた。

型チェックは「型を消した箇所が全部エラーになる」ことを保証しない。**削除のときは grep も併用する。**

### 2. テストがまた素通りしていた

`previewCandidates は storage に書かない` は、**バグを入れても落ちなかった**。

```ts
await previewCandidates({ minClusterSize: 5, minSharedItems: 2, lookbackDays: 3 }, NOW);
expect(await storage.getSettings()).toEqual(DEFAULT_SETTINGS);
```

渡していた値が `DEFAULT_SETTINGS` そのもので、**「書かなかった」と「同じ値を書いた」が区別できていなかった**。既定値と違う値に変えたら RED になった。

Phase 4b でも同種の素通り（storage モックの同期書き込みで順序が崩れていた）を踏んでいる。**「テストを書いた」と「テストが効いている」は別物**という同じ教訓の 2 度目。

### 3. `Object.entries` の値が `any` になり lint に落ちた

`getFeedback` で `Object.entries(stored)` の値が `any` になり、`@typescript-eslint/no-unsafe-assignment` が発火した。`Record<string, unknown>` に落としてから絞り込む形に変えた。**`unknown` なら `===` で literal 型に narrowing でき、型で守れる。**

## 実装後に見つかった UI の欠陥（ユーザー指摘）

### スライダーがつまめない

**条件のスライダーを候補一覧の下に置いていた。** ドラッグすると `input` → 再検出 → 一覧の差し替えが走り、件数が変わって一覧の高さが変わる。**その下にあるスライダーが指の下から逃げる。**

```
[候補一覧]   ← ドラッグ中に件数が変わり、高さが変わる
[スライダー] ← その下にあるので、つまみが動く
```

最初、原因を 2 つ（レイアウトシフトと value の書き戻し競合）と報告したが、**書き戻しは `await` の前に同じ値を書くだけで無害**だった。コードを読んで訂正した。原因は 1 つ、要素の順序である。

### 直したもの

| | 内容 |
|---|---|
| 順序 | 条件を候補一覧の **上** へ移した。増減するのは常に下側だけになる |
| 折りたたみ | `<details>` で閉じておく。日常は「候補を見て判断する」だけの画面にする |
| 見出し | 閉じたままでも `判定の条件（N≥5 M≥2 直近3日）` と現在値が読める |
| 分離 | `renderSliderInputs`（init のみ）と `renderSettingLabels`（毎回）に分けた |

### 置き場所の判断

「トークン設定のように別画面にすべきか」という問いに対しては、**ポップアップに残した**。

| | トークン | 判定条件 |
|---|---|---|
| 変更頻度 | 一度きり | 結果を見て何度か |
| 結果との関係 | 無関係 | **結果そのものを変える** |
| 効果の確認方法 | 「フルモードで動作中」と出る | **候補一覧を見るしかない** |

**近接は要る。目立たせる必要は無い。** 効果が候補一覧にしか現れない以上、別画面に出すと「動かす → 別画面 → 確認 → 戻る」になる。Phase 9 はその調整をやり込むフェーズである。一方で日常操作は閾値いじりではないので、折りたたんで主画面から退かせた。

### テストは実ファイルの順序を固定した

jsdom の骨格モックに対して順序を検査しても、それはモックを検査しているだけになる。**実際に配布される `index.html` を Vite の `?raw` で読み込み**、`id="conditions"` が `id="candidates"` より前にあることを固定した。条件を後ろに戻すと 2 件落ちる。

`node:fs` を使う手もあったが、tsconfig の `types` に `node` を足すことになり、**拡張のコードから node API が見えてしまう guardrail を失う**。`vite/client` に留めた。

### 落ちようがないテストを 1 件削除した

「ドラッグ中にスライダーの値を書き戻さない」を書いたが、**変異を入れても落ちなかった**。書き戻す値は直前に同じ入力から読んだ値なので、jsdom では観測差が出ない。

`renderSliderInputs` / `renderSettingLabels` の分離自体は防御として残したが、**テストで守られていないことをコードのコメントに明記**した。偽の安心を残すより、守られていないと書く方がよい。

## スライダーが摘まめない — 2 度目の指摘で真因が出た

1 度目の修正（条件を一覧の上へ移す）では **直らなかった**。レイアウトを疑ったのが間違いで、**原因は 1 回の `input` あたりの処理量**だった。

つまみを 1 px 動かすたびに、

1. `storage.local.get(null)` で **storage 全体**を読む（`getLikeIndex`）
2. **もう一度** `get(null)` で全体を読む（`getFeedback` も `readRaw` を通る）
3. 308 アカウント / 363 レコードに対して `detectCandidates` を回す
4. 候補一覧の DOM を全部作り直す

`input` はドラッグ中に毎秒数十回発火する。描画スレッドが飽和し、つまみがポインタに追従しなくなる。

### 直したもの

| イベント | 直前 | 修正後 |
|---|---|---|
| `input`（ドラッグ中） | 再検出 ＋ 一覧の再構築 | **数字の表示だけ（同期処理のみ）** |
| `change`（離したとき） | 保存 ＋ 再検出 | 変更なし |

`previewCandidates` は呼び出し元が無くなったので削除した。ライブプレビューは失われるが、**つまめないスライダーにライブプレビューが付いていても意味が無い。**

あわせて **判定ボタンでも再検出していた**のをやめた。閾値は変わっていないので、手元の views を 1 件だけ差し替える。ボタン 1 回ごとに storage 全体を読む必要は無かった。

### そのほかの指摘

| 指摘 | 対応 |
|---|---|
| 一つのページスクロールに | 候補一覧の `max-height` / `overflow-y` を外した。入れ子のスクロールは、どちらが動くのか分からなくなる |
| JST にしたい | `formatJst` を追加。`Intl.DateTimeFormat` に `timeZone: 'Asia/Tokyo'` を明示するので実行環境に依存しない |
| N/M ではなく日本語で | 見出しを `判定の条件（5 アカウントが 2 記事に共通 / 直近 3 日）` に。候補カードの文言と語彙を揃えた。scanner のログも `N>=` → `accounts>=` に（ログは英語のまま） |

### 「原因はレイアウト」と 2 度断定して 2 度外した

1 度目は「レイアウトシフトと value の書き戻し、2 つ」と報告し、コードを読んで「1 つ」に訂正した。2 度目は「1 つ、順序だ」と断定したが、それも違った。

**症状（つまみが動かない）から原因（描画スレッドの飽和）へ、見た目の理屈で飛んでいた。**`input` ハンドラが何を呼んでいるかを最初に数えていれば 1 度で着いた。UI の不具合を見た目の問題だと思い込むと、計算量を数えない。

## トークンの案内が無かった

ポップアップには `トークンを設定する` という **裸のボタンが一番下にあるだけ**だった。options ページには「設定すると著者の過去記事まで辿れるようになり、検出の射程が広がります」という説明があるのに、ポップアップ側には無い。

**429 に当たってから初めて存在に気づく置き方**になっていた。

### 直したもの

動作モードの案内を **候補一覧より上** に置いた。

| 状態 | 出るもの |
|---|---|
| 未設定 | 「ライトモードで動作中」＋「いま画面に出ている記事だけを見ます。トークンを設定すると著者の過去記事まで辿れ、枠が 60 → 1000 リクエストに広がります」＋ **[トークンを設定する]** |
| 設定済み | 「フルモードで動作中」＋「著者の過去記事まで辿ります。1000 リクエストまで」＋ **[トークンを変更する]** |

枠の数値は `RATE_LIMIT_ANON` / `RATE_LIMIT_AUTH` から作る（UI に直書きしない）。定数を直書きに戻すとテストが落ちる。

### 生のトークンをポップアップに渡さない

必要なのは「設定されているか」の真偽だけなので、`storage.hasToken()` を新設した。`getToken()` を呼ぶと生のトークンが `PopupState` に載りうる。

テストは `JSON.stringify(state)` にトークン文字列が含まれないことまで見ている。`hasToken()` を `getToken()` に戻すと落ちる。

### ついでに見つかった古い文言

`token-form.ts`（options ページ）が **「トレンド 30 件の範囲で検出します」** と書いていた。改訂 6 で件数は表示依存になり、実測は 25 件である。**Phase 4b の変更が UI の文言まで追いついていなかった。**

「いま画面に出ている記事の範囲で検出します」に直し、ポップアップ側にも「30 件と断定しない」ことをテストで固定した。

## 検証ループの差分レビューで見つかった欠陥

### キーボード操作で同じ storm が再発していた

マウスのドラッグは `input` を止めて直したが、**`change` を見落としていた**。

マウスなら `change` は「つまみを離したとき 1 回」だが、**キーボードの矢印キーはリピートのたびに発火する**（押しっぱなしで毎秒数十回）。1 回ごとに storage 全体の読み込みと検出が走り、さらに `storage.sync` への保存も走る（**1800 writes/hour**）。

つまり **マウスで踏んだのとまったく同じ問題が、キーボード経路で残っていた。**

落ちるテストで確認した: `change` を 5 回発火 → `applySettings` が **5 回**。

250 ms のデバウンスで 1 回にまとめた。**最後の値が使われる**ことも別途固定している（初回値を使う変異で 2 件落ちる）。

### 直したのが一方の入力手段だけだった

「`input` を軽くする」で直したつもりでいたが、直したのは**マウスの経路だけ**だった。同じ処理に入口が 2 つ（`input` / `change`）あり、片方しか見ていない。

**Phase 4b で「ログ水準の修正は経路ごとに漏れる」を踏み、Phase 6 では「性能の修正が経路ごとに漏れた」。**同じ形の失敗が層を変えて出ている。

## マルチエージェントレビューで見つかった欠陥（2 回目）

3 次元（品質・TypeScript・セキュリティ）で並列レビュー。**HIGH 1 件・LOW 3 件。**

### HIGH: デバウンスは「保留中のタイマー」しか束ねていなかった

`applyTimer` はタイマーが発火した瞬間に `null` に戻る。**実行中の適用は次の適用を止めない。**

```
t=0     change → タイマー
t=250   発火。applyTimer=null。適用 A 開始（storage 全体 ×2 + 検出 + 書き込み ×2）
t=300   change → 新しいタイマー（A はまだ実行中）
t=550   発火。適用 B 開始 ← **A と重なる**
```

落ちるテストで確認した: A の完了を止めた状態で 2 回目を投げると、**A の終了前に B が始まる**。

`applyChain` に直列でつなぐ形にした。次の適用は前が終わってから始まるので、**最後に走ったものが最後に書く**ことが順序として保証され、そのとき読むスライダーの値も最新になる。

**兄弟の `handleVerdict` は同じ危険を `busy` フラグで防いでいた。**片方だけ守られていた。

### レビュアーの確度 0.55 をどう扱ったか

反証側は「Chrome の storage は領域ごとに FIFO なので、A が常に 1 歩先を行き、結局 B が最後に書く」と指摘し、確度を 0.55 に留めた。**この指摘は正しい。**

それでも直したのは 2 つの理由による。

1. 順序が保たれても **storage 全体の読み込みが 2 本と検出が 2 回**走る。デバウンスが防ごうとしていた飽和そのもの
2. FIFO は実装の性質であって仕様ではない。この経路は `local → sync → local` と領域をまたぐ

**「たぶん大丈夫」を根拠に残すより、2 行で消せる不確実性は消す。**

### LOW 3 件

| 指摘 | 対応 |
|---|---|
| `recordVerdict` が storage を読み直している | `saveVerdict` がマージ結果を返す形に。1 クリックあたりの往復が 3 回 → 2 回 |
| スライダーの値を可動域に丸めていない | `RANGES` で丸める。HTML の max と `RANGES` がずれても範囲外が sync に入らない |
| **Prettier の整形ずれが 10 ファイル** | `npm run format` を実行 |

### 整形が一度もかかっていなかった

`npx prettier --check` が **10 ファイル**を報告した。うち 4 つは Phase 6 以前（`qiita-client.ts` など）で、**Phase 4b の作業でも整形せずにコミットしていた**。

`npm run lint` は ESLint だけで整形を見ない。`npm run format` はどのゲートにも入っていない。**「lint が通った」で整形も通ったと思い込んでいた。**

## 記事化の素材

- **寿命の違うデータを同じ構造に入れてはいけない。** 「候補」は閾値を変えるたびに再計算で作り直されるが、「評価」は人間が積み上げた資産で再計算では復元できない。`Candidate.verdict` のままだと、**スライダーを 1 つ動かした瞬間に指標そのものが消えていた**
- **型を消しても、消し忘れは型チェックで全部は出ない。** `.map<T>()` 経由の object literal は余剰プロパティ検査が効かず、`verdict: null` を実行時に書き続けていた。削除のときは grep も併用する
- **テストがまた素通りしていた（2 度目）。** 今回はフィクスチャが既定値そのもので、「書かない」と「同じ値を書く」が区別できていなかった。**変異を入れて落ちることを確かめる手順が無ければ、両方とも永久に嘘の緑を返していた**
- **UI の手抜きが指標の妥当性を殺す。** 根拠記事へのリンクが無ければユーザーは記事を読めず、「妥当 / 誤り」は当てずっぽうになる。そこから出る適合率は無価値。**リンクは飾りではなく指標の一部**
- **「候補が変わるのを見ながら閾値を調整する」は、そのまま作ると操作不能になる。** 結果を上、操作を下に置くと、結果の変化が操作対象を動かす。**動くものの下に、つまむものを置いてはいけない**
- **仕様を変えても、文言は自動では追いつかない。** 改訂 6 で「トレンドの件数は表示依存」になったのに、options ページは「トレンド 30 件」と言い続けていた。**型でもテストでも捕まらない種類の嘘**で、実測 25 件を見た人が読むと混乱する
- **説明の無いボタンは、押す理由が無いのと同じ。** ポップアップの一番下に「トークンを設定する」だけ置いていた。得られるもの（射程 ＋ 枠 60 → 1000）を書いて上に出すまで、429 に当たるまで気づかれない置き方だった
- **UI の不具合を「見た目の問題」だと思い込むと、計算量を数えなくなる。** つまみが動かない原因を 2 度レイアウトのせいにして 2 度外した。真因は `input` 1 回あたり storage 全体を 2 回読んで 300 アカブンの検出を回していたこと。**`input` は 1 px ごとに発火する**
- **デバウンスは「呼び出しの頻度」を下げるが「同時実行」は止めない。** タイマーは発火した瞬間に手を離すので、実行中の処理は次を止めない。頻度の制御と排他は別の問題
- **`npm run lint` が通っても整形は通っていない。** ESLint は整形を見ず、`npm run format` はどのゲートにも入っていなかった。10 ファイルが静かにずれ、レビューで初めて出た。**ゲートに無い工程は実行されない**
- **確度 0.55 の指摘をどう扱うか。** 反証側の「たぶん FIFO なので実害は出ない」は正しかった。それでも直した。**2 行で消せる不確実性を「たぶん大丈夫」で残す理由が無い**
- **同じ処理に入口が 2 つあると、片方だけ直して直ったつもりになる。** マウス（`input`）の storm は直したが、キーボード（`change` のリピート）は残っていた。Phase 4b の「ログ水準の修正は経路ごとに漏れる」と同じ形が、性能の層で再発した
- **キーボード操作は「たまにしか使われない経路」ではない。** 矢印キーのリピートは毎秒数十回で、マウスのドラッグより負荷が読みにくい
- **「ドラッグ中にライブプレビュー」は、素直に実装すると操作そのものを殺す。** プレビューの計算がドラッグの応答性を食う。`input` は同期処理だけ、重い処理は `change` に置く
- **落ちようがないテストは、消すか「守られていない」と書く。** 残すと、次に触る人が守られていると思って壊す
- **受け入れ基準を絶対形で書くと、正しい実装が基準に反する。** 「`logger.error` を増やさない」と書いたが、本来の規約は「**想定内の失敗を**載せない」だった。基準は禁止したい失敗の形で書くべきで、数で書くべきではない
